# Runtime 说明

[English](runtime.md) | [简体中文](runtime.zh-CN.md)

TinyHarness 负责把模型与工作区中的工具连接起来。收到任务后，它将对话和可用工具发送给模型，
检查模型返回的工具调用，执行调用，再把结果加入对话。下一轮，模型根据这些结果继续工作，
或给出最终回答。整个循环同步执行，工具调用也按顺序逐个运行。

本文面向需要配置运行或扩展 TinyHarness 的开发者，介绍这条执行流程及其限制。
安装方式和设计取舍见[项目 README](../README.zh-CN.md)。

## 执行与故障

CLI 使用 `AgentSession` 保存多次提交之间的对话。每次提交都会加入用户的新任务，然后进入
[Agent 循环](../tiny_harness/agent/loop.py)，直到返回回答。Python 调用方也可以通过
`run_agent()` 配置并调用同一个循环，自行管理传入的消息。

每轮开始时，运行时先整理要发给模型的对话；如果上下文预算不足，就缩减内容。随后发送请求，
并在写入历史前验证模型响应。如果响应中包含工具调用，就执行这一批调用，依次记录对应结果，
再请求模型生成下一次响应。如果没有工具调用，响应文本就是最终回答。

每次运行都有轮次上限。最后一轮专门用于收尾：请求中不再提供工具，而是要求模型根据已有信息
给出回答。即使模型仍然返回工具调用，也不会执行。对于已通过协议校验、但仍包含工具调用、
工具协议文本或没有回答正文的响应，运行时会重试一次；再次无效时，返回固定的失败提示。
具体处理见[模型轮次实现](../tiny_harness/agent/turn.py)。

### 运行失败后如何处理

普通工具错误会作为工具结果返回给模型，模型可以在后续轮次中据此调整。模型服务的临时错误
也可以在同一逻辑轮次内重试。Hook 执行失败、事件日志失败或模型响应结构不合法，则会终止运行。

一次非空提交开始后，只要有异常或中断向外传播，Session 就会保持失败状态。之后再提交任务，
会抛出 `SessionFailedError`，直到调用方执行 `clear()`。空输入在提交前就会被拒绝，
不会使 Session 进入失败状态。

清空失败的 Session 前，应先检查工作区。运行中止时，一批工具调用可能尚未完成，但之前的调用
已经修改了文件或启动了进程。运行时不会补造缺失的结果、重新执行调用，也不会撤销这些影响。
`clear()` 只清空对话历史并重置失败状态。直接调用循环的调用方，需要自行丢弃或重建失败的运行。
参见 [Session](../tiny_harness/agent/session.py) 和
[批次生命周期测试](../tests/test_batch_lifecycle.py)。

## 工具与运行能力

### 工具发现

模型能使用哪些工具，取决于本次运行是否配置了工具所需的组件。例如，没有配置测试执行器，
就不会提供 `run_tests`。依赖子 Agent 执行器或技能清单的工具也遵循这一规则。

要提供工具，`tiny_harness/tools/` 下的模块需要导出 `build_tools(context)` 函数。
运行时按模块名排序，依次调用这些函数，并传入本次运行的上下文。函数返回可用的
`ToolDefinition` 对象；缺少所需组件时，也可以不返回任何工具。每个工具定义包含名称、描述、
参数 schema、处理函数，以及可选的、可安全记录到日志中的追踪元数据。

[工具注册表](../tiny_harness/tools/registry.py) 检查名称是否重复、查找工具，并根据这些定义
生成发送给模型的工具 schema，无需另行维护一份内置 schema 列表。工具通过扫描目录发现，
不支持热重载或入口点插件。新增工具时，还必须检查权限策略如何处理这个工具名。
[工具架构方案](superpowers/plans/2026-09-04-tool-architecture-phase-1.md)记录了最初的设计；
具体行为以当前代码为准。

### 校验与执行

在写入 assistant 消息或执行任何工具之前，运行时会先校验整个模型响应。调用 ID 必须非空，
且在同一批次中不能重复；协议字段和结束原因也必须合法。批次无效时会抛出 `ModelProtocolError`，
不会先执行其中一部分。JSON 解码失败和工具参数错误则按单次调用处理：错误会成为该调用的结果，
不会导致同批次中其他合法调用被丢弃。

所有工具都经过同一条分发流程：

```text
查找工具 / 解码参数 → 前置 Hook → 权限检查 → 开始事件
                   → 处理函数 → 后置 Hook → 结果事件 → 返回
```

前置 Hook 可以在权限检查前阻止调用。权限决策分为 `ALLOW`、`DENY` 和 `ASK`；
`ASK` 未获得批准时，按拒绝处理。被 Hook 阻止或被权限策略拒绝的调用，都不会进入处理函数。
指定 Shell 的工作目录并不等于提供了操作系统沙箱。

工具按模型给出的顺序逐个执行，结果也按相同顺序加入历史。所有 `TOOL_CALLED` 事件会在开始
分发前发出；`TOOL_STARTED` 则在即将执行处理函数时发出。处理函数的一般错误会转为
工具结果，而 Hook 执行失败和事件日志失败会向外传播，终止本次运行。

### 代码读取与搜索

可先用 `code_outline(path, max_symbols=200)` 定位 Python 定义，再用 `read_file` 按行读取。
它使用标准库 AST 解析器读取工作区内的 `.py` 文件，不导入或执行源码。返回的大纲按源码顺序
列出类、函数、异步函数和方法，并用缩进表示嵌套关系。行号从 1 开始，包含起止行；
起始行指向 `class` 或 `def`，不包含装饰器。

输入文件最大为 2 MiB。输出默认最多列出 200 个符号，可配置至 500 个，同时受 30,000 字符
上限限制。截断、文件中没有定义、语法错误和无效路径都会有明确提示。该工具同样经过共享分发
和工作区路径检查，默认权限策略允许调用。它仅支持 Python 源码，不做符号解析、索引或调用图分析。

`search_code` 和 `grep` 都可以用 `include` 文件匹配模式缩小内容搜索范围，模式相对于
`path` 匹配：`**/*.py` 匹配任意深度的文件，`*.py` 只匹配当前目录下的文件，
`src/**/*.py` 匹配指定子树。递归搜索会跳过目录符号链接，以及 `.git`、`.venv`、`venv`、
`node_modules`、`__pycache__`、`.pytest_cache`、`.mypy_cache`、`.ruff_cache`、`.tox` 和 `.nox`。

要搜索被排除的目录或文件，需要将 `path` 显式指向它；仅设置 `include` 不会覆盖排除规则。
直接指定文件时，不再按 `include` 筛选，但仍会检查工作区边界。上述按目录名排除的规则，
不适用于通过 `glob` 和 `list_files` 查找文件。

### 委派任务与 Todo

模型可以通过 `task` 委派任务。父 Agent 会等待子 Agent 使用一组全新的消息完成运行，
然后将子 Agent 的最终文本作为工具结果接收。两者共享工作区和模型服务接口，因此子 Agent
对文件的修改会直接反映在父 Agent 的工作区中。

子 Agent 继承父 Agent 的策略和能力，但有独立的轮次预算、错误恢复状态、上下文和待办事项。
它不能继续创建子 Agent，也不会提取持久化记忆。`todo_write` 用于更新本次运行的待办状态，
与跨运行保存的持久化记忆分开管理。

## Context 与恢复

工具不断返回结果，对话也会逐渐变长。TinyHarness 区分两份相关内容：一份是在轮次之间保存的
对话历史，代码中称为 canonical history；另一份是为某次模型调用准备的请求。对话历史由
运行时维护，可以被压缩，因此不是一份不可修改的完整记录。

准备请求时，运行时会复制这份历史，缩短过大的 `read_file` 结果，并加入只用于当前请求的
运行指导。这一步在代码中称为 request projection。它不会缩短已保存的历史，也不会生成落盘文件。
即使关闭上下文压缩，请求仍会经过这一步处理。

配置上下文预算后，运行时会同时计算消息和工具 schema 的大小。超过预算的 80% 时，先把
工具结果保存到文件，再用较短的预览替换历史中的正文，目标是降到预算的 55%。只有这样仍然
缩减不足时，才请求模型生成历史摘要。如果必须保留的历史使 55% 的目标无法实现，则允许退回
80% 的上限。当前用户请求，以及调用和结果的完整配对关系都会保留；必要内容仍放不下时，
准备过程会明确报错。正常轮次不会主动生成工作检查点。

模型服务的临时错误会复用已准备的请求重试。上下文长度错误则需要不同的处理：开启压缩时，
运行时可以重新压缩历史并构建请求，每个逻辑请求最多尝试一次。缩减目标不超过失败请求的
75%，同时仍须遵守硬预算。

自动压缩和因长度错误触发的压缩，都要求摘要保留事实证据和不确定性，不判断工作是否就绪，
也不指定后续行动。参见[上下文实现](../tiny_harness/runtime/context.py)和
[上下文不变量测试](../tests/test_context_invariants.py)。

这里的 token 数量是估算值。默认方法根据紧凑 JSON 的长度计算，约每四个字符一个 token；
Python 调用方可以传入自己的 `token_meter`。
[上下文归因说明](context-attribution.md)介绍了请求大小如何拆分，以及这些估算与模型服务
计费用量的区别。

## Skills 与 Memory

技能（Skills）提供模型可以按需加载的操作指导。TinyHarness 在以下位置查找
`<name>/SKILL.md` 文件，文件的 YAML 中需包含 `name` 和 `description`：

- 内置目录 `tiny_harness/skills/`；
- 用户目录 `~/.tinyharness/skills/`；
- 工作区目录 `.tinyharness/skills/`。

Session 保存创建时发现的技能清单。模型最初只收到有大小限制的清单信息，需要正文时再调用
`load_skill`。要发现新增或变更的技能，需要新建 Session。技能正文是不可信的指导内容，
不能覆盖指令、权限、Hooks 或工作区边界。
[技能设计](superpowers/plans/2026-09-04-formal-skills-phase-2.md)提供了设计背景。

持久化记忆（Memory）用于在多次运行之间保存稳定偏好、反馈、项目事实和引用，不保存当前计划
或执行状态。通过 `--memory` 启用后，文件保存在工作区的 `.tinyharness/memory/` 下。

准备本次运行时，系统会选择相关记忆条目并加入对话历史，用标记限定它们在本次运行中使用。
主 Agent 生成最终回答时，最终回答 Hook 会提取值得长期保留的信息，并可能整合已有条目。
普通的提取或整合失败不会丢弃回答；`EventLogError` 仍会终止运行。参见
[记忆实现](../tiny_harness/memory/)。

## Hooks 与事件

Hooks 用于在工具执行前后运行扩展代码，事件则用于观察执行情况。
[Hooks 示例](../examples/hooks_demo.py)在前置 Hook 中阻止 `write_file`，在后置 Hook 中观察结果。
按快速开始完成项目安装后，在仓库根目录运行：

```powershell
python examples/hooks_demo.py "Inspect this project" --workspace .
```

库调用方默认不记录事件。CLI 根据事件向 stderr 输出进度，并将单次运行的最终回答写入 stdout。
JSONL 日志可以与终端输出同时启用。事件记录模型请求与响应、工具从调用到结束的过程及执行耗时、
上下文变化和父子调用之间的关联。终端进度不会包含工具结果正文。

## CLI 与本地验证

必须设置 `TINYHARNESS_API_KEY`。`TINYHARNESS_MODEL` 和 `TINYHARNESS_BASE_URL`
用于配置模型和服务端点，示例值见 [`.env.example`](../.env.example)。
省略任务参数会进入复用同一 Session 的 REPL。

运行 `python -m tiny_harness --help` 查看完整选项列表：

| 选项 | 用途 / 默认值 |
| --- | --- |
| `--workspace` | 工作区目录；当前目录 |
| `--max-turns` | 主 Agent 轮次上限；20 |
| `--max-model-retries` | 每个逻辑请求的临时错误重试次数；2 |
| `--max-context-tokens` | 估算上下文预算；125000 |
| `--no-context-compaction` | 关闭预算和压缩，仍会整理模型请求 |
| `--subagent-max-turns` | 子 Agent 轮次上限；10 |
| `--event-log` | 将生命周期事件追加到 JSONL 文件 |
| `--memory` | 启用工作区持久化记忆 |
| `--quiet` / `--verbose` | 减少进度输出 / 增加运行细节 |

测试使用返回预设响应的模型替身和本地测试数据，不调用真实 API：

```powershell
python -m unittest discover -s tests -v
```

各模块的测试命令，以及扩展时需要遵守的约定，见 [AGENTS.md](../AGENTS.md)。
